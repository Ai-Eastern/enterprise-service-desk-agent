# v0.1 业务与团队

## 阶段定位

`v0.1` 对应 2024.09–2024.12。2024.09 起，既有 Dify 企业知识助手继续承担业务交付，自主 Agent 底座作为旁路验证；2024.12 完成可运行快照和依赖冻结。不能把 12 月发布的依赖描述成 9 月已经使用。

本阶段不是为了展示 LangGraph 或向量数据库，而是解决政企内部服务台的三个问题：知识回答必须有来源且不越权，已知服务异常应先查询状态而不是重复建单，真正产生业务写入时必须经过人工确认并避免重复执行。

## 业务场景

演示组织为“智达科技”，所有组织、身份、产品和数据均为虚构脱敏内容。

| 角色 | 主要诉求 | 允许行为 |
| --- | --- | --- |
| 普通员工 `readonly-demo` | 查询制度、操作方法和服务状态 | 查看公开知识与状态，不允许创建工单 |
| 客服 `support-demo` | 辅助员工诊断并处理无法自助解决的问题 | 查看公开/客服知识，查询状态，发起需人工确认的工单 |
| 管理员 `admin-demo` | 处理升级事项并查看更高权限资料 | 查看全部演示知识，执行授权范围内操作 |

核心业务故事为：

```text
员工报告知识中心响应缓慢
  → Agent 检索公开知识并返回引用
  → 查询服务状态，发现 knowledge-hub 处于 degraded
  → 能直接解释的问题不建单
  → 无法解决时由客服形成工单草案
  → LangGraph 在写入前中断，等待人工批准
  → 批准后写入 SQLite 工单
  → 相同幂等键重试时复用原工单
  → 审计记录 created / reused 结果
```

## 我的职责

我的角色是服务端核心模块开发者，不是整个项目的人员经理。主要职责包括：

- 将知识查询、状态查询和建单请求拆成可测试的业务路径。
- 设计 `user_id → role → visibility` 的可信上下文和查询阶段过滤。
- 使用 LangGraph 表达写操作前的人工中断与恢复。
- 使用稳定 thread ID、SQLite checkpoint 和幂等键控制重复执行。
- 设计工具输入、输出和错误合同，配合后端完成业务接口对齐。
- 建立权限、引用、审批、重复请求和异常路径的固定回归。
- 对产品、前端、测试和实施解释能力边界，并提供可复核的演示证据。

我不单独负责业务需求最终拍板、前端视觉设计、生产 IAM、生产基础设施审批或客户上线验收。

## 疑难问题与解决过程

### 检索权限不能只写在提示词里

问题：如果先检索全部文档再让模型“不要回答”，敏感内容已经进入上下文，提示词无法构成可靠隔离。

处理：由可信身份映射得到允许的 `visibility`，在 Chroma 查询阶段直接过滤；未知身份 fail closed。

取舍：公开仓库只使用三个固定演示身份。这样可验证权限合同，但不冒充真实 IAM 接入。

### 人工审批恢复可能产生重复工单

问题：进程重启、审批恢复或调用方重试可能重复执行写操作。

处理：用稳定 thread ID 保存检查点，以幂等键绑定用户、角色、产品和摘要；完全相同的请求复用原工单，参数或主体变化则冲突失败。

取舍：只对有副作用的建单使用人工门禁，知识和状态查询不增加无意义审批。

### 历史依赖在 Windows 上存在 API 和资源释放差异

问题：LangGraph 0.2.60 不允许节点名与 state key 同名；Chroma 0.5.23/HNSW 在 Windows 测试临时目录中需要显式停止客户端，否则句柄影响清理。

处理：将答案节点命名为 `compose_answer`；在检索客户端使用 `try/finally` 停止 Chroma system 并清理共享缓存；测试中的 SQLite 断言连接显式关闭。

取舍：不升级到未来版本规避问题，而是在 2024-12-31 冻结版本内做最小兼容修复，保留时间线真实性。

### 环境可重复性不能依赖开发机现状

问题：系统 Python、用户 site-packages、缓存和外部 pip 配置会造成“同一 requirements、不同结果”。

处理：固定 Python 3.10.11 x64、精确依赖集合和项目内缓存/临时目录，健康检查验证解释器路径、前缀、版本和安装集合。

取舍：环境证明只覆盖当前 Windows 本地运行，不扩大为其他机器或生产部署证明。

## 工程取舍

| 决策 | 选择 | 暂不选择 | 原因与代价 |
| --- | --- | --- | --- |
| 编排形态 | 单 Agent + 明确路由 | 多 Agent | 当前主要问题是权限、审批和幂等；提前拆 Agent 会增加通信和调试成本 |
| 向量存储 | Chroma 本地持久化 | Milvus 集群 | 便于试点启动和测试；代价是不能证明生产容量和高可用 |
| 状态与工单 | SQLite | PostgreSQL/Redis | 满足单机快照与幂等验证；代价是并发、容灾和集群能力未覆盖 |
| 身份 | 固定演示身份 | 真实政企 IAM | 公开仓库不接触真实账户；代价是不能声称生产认证 |
| 写操作 | 人工批准后执行 | Agent 自动写入 | 降低误操作风险；代价是增加人工等待和流程状态管理 |
| 数据 | 虚构脱敏固定数据 | 真实客户数据 | 可公开复现并降低合规风险；代价是效果不能外推到真实语料 |

## 当前证据

- Python 3.10.11 x64 环境和 118 个精确锁定依赖通过健康检查。
- `pip check` 通过。
- v0.1 全量 12 项测试通过。
- 本地 RAG 演示返回 5 条公开可见结果。
- 建单在人工批准前中断，且此时没有工单数据库副作用。
- 批准后创建 1 条工单；相同幂等键再次执行复用同一工单。
- 最终演示记录为 1 条工单、2 条 created/reused 审计事件。

这些结果证明本地虚构脱敏数据上的单 Agent/RAG 业务闭环，不证明真实国企部署、生产 IAM、真实工单系统、生产容量、GUI 或用户验收。

## 为什么进入 v0.2

v0.1 已证明核心业务工具可以在项目内部安全调用，但其他客户端仍需要编写专用适配代码。下一阶段的真实问题是工具发现、参数 Schema 和调用合同如何标准化，因此只对低风险只读能力开展 MCP 内部试点；建单写操作继续留在人工门禁内。

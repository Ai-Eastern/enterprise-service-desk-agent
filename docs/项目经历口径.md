# 项目经历口径

## 目的

本文件约束 `v0.1 → v0.2 → v0.3 → v1.0` 的履历叙事。版本不仅演进技术，也必须同步说明业务范围、团队投入、阶段分工、个人职责、疑难问题、工程取舍、交付证据和能力边界。

仓库使用当前真实 Git 提交重建能力快照，不伪造 2024、2025 年的提交日期。历史团队人数采用“阶段核心投入人数 + 约 10 人跨职能协作池”的复盘口径，不冒充精确编制、考勤或人事记录。当前 Codex 任务中的项目经理、技术负责人和工程师只代表开发调度，不属于历史公司团队。

## 履历基线

- 任职主体：西安烽火软件科技有限公司，2023.09 至今。
- 项目名称：RAG 驱动的 Agent 工具协同平台，2024.09 至今。
- 前序能力：Dify 企业知识助手，2023.10–2024.12。
- 双轨阶段：2024.09–2024.12，既有 Dify 应用继续交付，自主 Agent 底座旁路验证。
- 个人定位：AI Agent 应用开发工程师、服务端核心模块开发者，不描述为公司级项目经理或部门负责人。
- 个人主责：数据入库、检索链路、Agent 状态编排、工具合同、Python 服务定制、业务接口集成、评测与回归验收。
- 协作边界：产品需求和业务验收由产品/业务人员共同确认；前端体验、生产 IAM、基础设施审批和上线决策不归个人单独负责。

## 团队规模口径

整个项目使用约 10 人的跨职能协作池。人员不会为每个版本全部满负荷投入，核心投入随业务复杂度增加，联调、验收和故障处理阶段允许短期浮动。

| 阶段 | 核心投入 | 高峰投入 | 主要参与角色 | 人数变化原因 |
| --- | ---: | ---: | --- | --- |
| v0.1 | 约 5–6 人 | 约 7 人 | 产品/业务、本人、AI/数据、后端、测试，实施或安全按需参与 | 先验证单 Agent 服务台闭环，避免需求未稳定时扩大团队 |
| v0.2 | 约 6–7 人 | 约 8 人 | v0.1 核心成员 + 系统集成、安全/运维 | MCP 试点增加协议适配、身份边界和接入验收工作 |
| v0.3 | 约 7–8 人 | 约 9 人 | 服务台侧、诊断/运维侧、后端集成、测试、安全 | A2A PoC 涉及跨角色任务合同、状态和失败回传 |
| v1.0 | 约 8–9 人 | 约 10 人 | 产品、Agent/RAG、后端、前端、测试、运维/安全 | 多 Agent 收敛需要统一入口、交接、审计、可观测和回归治理 |

上述数字是保守复盘口径。面试中使用“约”“核心投入”“联调高峰”等限定词，不回答成精确人事编制。

## 四阶段完整演进

### v0.1 2024.09–2024.12

- 业务目标：将制度问答、服务状态查询和需要人工确认的工单写入串成最小闭环。
- 团队分工：产品/业务整理场景和验收；本人负责 RAG、状态编排、工具合同和回归；后端协作服务目录和工单接口；AI/数据协作文档与检索；测试覆盖权限、审批和重复执行。
- 个人职责：把提示词层的要求下沉为查询阶段权限过滤、显式人工中断、稳定 thread ID、SQLite checkpoint 和幂等键。
- 疑难问题：权限可见性泄漏、恢复后重复建单、Windows 依赖和向量库句柄释放、LangGraph 版本 API 差异。
- 工程取舍：保留单 Agent；本地使用 Chroma/SQLite；写操作必须人工批准；公开仓库使用固定演示身份和虚构脱敏数据。
- 证据边界：可证明本地流程、测试和演示，不证明生产 IAM、真实国企数据、生产容量或用户验收。

### v0.2 2025.01–2025.06

- 业务目标：让不同调用方通过统一工具合同访问知识、状态等低风险能力，减少重复接口适配。
- 团队分工：本人负责 MCP 工具合同、Schema、错误映射和原业务能力复用；后端/集成人员负责调用方接入；安全人员审查身份和只读边界；测试负责发现、调用和异常合同。
- 个人职责：推动只读工具试点，保证 MCP 适配层不复制业务逻辑、不接受客户端伪造角色、不绕过写操作人工门禁。
- 疑难问题：早期 SDK 变化、工具 Schema 一致性、身份上下文传递、客户端生命周期和错误返回稳定性。
- 工程取舍：先开放一个只读工具；使用本地 stdio；不开放远程服务和建单写操作；只描述为内部试点。
- 时间线门禁：MCP 于 2024-11-25 公开；`mcp==1.9.4` 于 2025-06-12 发布，因此该版本只能作为 2025 年 6 月验收快照，不能表述为整个上半年一直使用 1.9.4。

### v0.3 2025.07–2025.12

- 业务目标：从一次工具调用扩展到服务台与诊断角色之间可跟踪的任务协作，明确成功、失败和结果回传。
- 团队分工：本人负责 Agent Card、任务状态和 artifact 合同；诊断/运维人员提供诊断规则；后端负责服务台侧接入；测试和安全覆盖失败终态、未知身份和越权场景。
- 个人职责：实现最小 A2A 通信 PoC，处理 `submitted → working → completed/failed`，并让失败显式进入终态。
- 疑难问题：协议和 SDK 快速变化、任务状态映射、跨角色错误语义、结果重复消费和边界不清。
- 工程取舍：只验证一个只读诊断 Agent；先做本地 PoC；不宣称跨厂商、跨网络或生产互操作。
- 时间线门禁：A2A 于 2025-04-09 公布，0.3 规范于 2025-07-30 发布，Python SDK 0.3.6 于 2025-09-09 发布。7–8 月只能描述需求和协议预研，0.3.6 实现只能从 9 月起描述。

### v1.0 2026.01–2026.09

- 业务目标：把知识、诊断、工单和审计能力收敛为统一服务台入口，支持职责分流、人工门禁、任务交接和失败恢复。
- 团队分工：产品负责业务路线；本人负责核心 Agent 编排、合同和回归；AI/RAG、后端、前端分别负责检索、接口和操作入口；测试、运维/安全负责故障、观测和上线边界。
- 个人职责：设计调度、知识、诊断、工单和审计的职责边界，统一任务状态、Trace、幂等和恢复规则，推动跨模块联调和固定回归。
- 疑难问题：Agent 职责重叠、任务交接丢状态、超时后的真实状态不确定、重放副作用、Trace 与业务任务关联。
- 工程取舍：优先采用进程内逻辑 Agent，不提前拆成分布式微服务；保留本地回退；外部中间件使用窄适配器；所有有副作用动作继续受权限和人工门禁控制。
- 证据边界：多 Agent 工程化不等于所有 Agent 独立部署，也不等于真实生产平台、高可用或大规模用户验收。

## 技术成熟度用语

| 状态 | 可用表述 | 禁止表述 |
| --- | --- | --- |
| 已有稳定业务使用和可复核证据 | 应用、接入、交付、运行 | 无证据的行业领先、全面生产化 |
| 技术刚发布或国内尚未广泛采用 | 内部试点、前期预研、PoC、兼容性验证 | 大规模应用、成熟落地、行业标准方案 |
| 只有接口或本地适配器 | 设计适配边界、本地回环验证 | 已接入生产集群、完成高可用 |
| 使用虚构数据和自动化测试 | 本地演示、固定回归、合成数据验证 | 真实客户数据、真实生产指标、用户验收 |

## 每个版本必须留下的经历材料

后续版本均新增一份独立阶段文档，至少包含：业务背景、团队规模、角色分工、个人职责、关键问题、定位过程、方案比较、最终取舍、代码/测试证据、业务结果、未完成事项和下一阶段触发原因。

任何技术进入版本前都必须核对官方发布日期、所用 SDK 精确版本发布日期和当时成熟度。发布日期满足不等于国内已经大量应用；缺少采用证据时统一降级为“内部试点、前期预研或 PoC”。

# 面试演示指南

## 一句话定位

这是一个以政企内部服务台为背景的 Agent 工程演进项目：先用 RAG 回答有依据的知识问题，再调用只读工具诊断服务；只有确实需要写入工单时，才进入权限校验、人工复核和幂等执行。

它不是工单审批系统，也不是只展示框架调用的空壳。当前仓库已经实现可运行的核心流程和本地基础设施适配；接入真实组织 IAM、知识库、工单平台和生产集群属于企业落地阶段。

## 三分钟讲法

### 0:00–0:30 业务问题

传统知识助手只能回答问题，无法安全地调用业务能力；普通自动化又容易把“回答”和“有副作用操作”混在一起。本项目把请求分为知识、诊断和工单三条路径，并让权限、人工门禁、幂等和审计贯穿工具调用。

### 0:30–1:30 当前架构

- triage 判断进入知识、诊断还是工单路径。
- knowledge 使用带 visibility 过滤的 RAG，并返回文档引用。
- diagnostic 调用只读服务状态工具，不需要人工审批。
- ticket 在 LangGraph 检查点中断，只有授权角色人工确认后才恢复。
- audit 记录 Agent、动作、结果和耗时，并创建 OpenTelemetry span。
- FastAPI 是业务入口；MCP stdio 只开放只读状态工具；A2A PoC 验证跨 Agent 任务状态与结果回传。

### 1:30–2:30 技术演进

- 2024 Q4：从 Dify 项目逐步下沉到自主可控的 Python/LangGraph RAG 服务台。
- 2025 H1：用 MCP 试点开放一个只读工具，不把建单暴露到协议边界。
- 2025 H2：用 A2A PoC 验证独立诊断 Agent 的任务状态、结果和失败回传。
- 2026：收敛为调度、知识、诊断、工单、审计五类 Agent 的工程化协作。

这些是能力阶段，不是伪造的历史 Git 日期。仓库用真实提交和标签重建演进差异。

### 2:30–3:00 证据与边界

- 100/100 条复合任务合同通过，覆盖路由、Schema、引用、权限和人工门禁。
- 30/30 条故障注入合同通过，覆盖身份、越权、超时、中断恢复、重复执行和人工拒绝。
- 40 条真实 Chroma 知识检索命中 39 条，Hit@5=0.975、MRR=0.85。
- PostgreSQL、Redis、Milvus 本地真实容器回环 3/3 通过。
- 1,000/1,000 条本地 ASGI 混合请求成功，并发 20。

这些结果不等于真实生产流量、生产 IAM、外部工单系统联调、高可用或用户验收。

## 常见追问

### 为什么建单需要人工审批？

审批只针对会写入业务系统的副作用操作。知识问答和状态查询不审批；建单则需要确认摘要、产品和权限，避免模型误判直接写入。人工门禁是风险控制，不是项目的全部业务。

### MCP 为什么只开放只读工具？

试点阶段先验证发现、Schema 和调用链路。`create_ticket` 留在内部 LangGraph 人工复核链，避免外部 MCP 客户端绕过审批。真实企业落地时可以继续扩展，但必须为写操作补齐可信身份、授权与审计。

### 这是不是一个壳？

它是可复用底座，但不是空壳。路由、权限、RAG 引用、人工中断恢复、幂等、MCP、A2A、追踪、固定评测和本地中间件回环都有代码和测试；真实客户的 IAM、知识数据、工单 API 与部署拓扑需要按项目替换适配器。

### 为什么不是所有能力都做成多 Agent？

简单只读查询不需要为了“多 Agent”增加通信成本。只有当任务需要独立职责、状态传递、失败隔离或跨团队服务边界时才拆 Agent；这比按技术名词堆角色更接近企业工程。

### 为什么没有声称生产落地？

公开仓库使用虚构数据，无法证明真实组织、真实用户和生产环境。面试时应把“设计与本地验证”和“生产验收”分开，这比无法复核的生产数字更可信。

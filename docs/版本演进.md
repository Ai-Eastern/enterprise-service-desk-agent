# 技术演进与版本说明

## 1. 文档目的

本项目不是把 RAG、MCP、A2A 和多 Agent 一次性堆在同一个 Demo 中，而是复现一条更接近企业软件建设节奏的技术演进路线：先用低代码平台验证需求，再把关键能力逐步下沉到自主服务，随后验证标准化工具调用和跨 Agent 通信，最后补齐权限、人工门禁、业务接口、可观测性和工程证据。

本文重点回答六个问题：

1. 每个时间段遇到了什么业务问题。
2. 为什么当时选择对应技术，而不是提前使用后续方案。
3. 相比上一阶段增加了哪些能力。
4. 仓库中有哪些代码和测试可以证明这些能力。
5. 当前证据能够说明什么、不能说明什么。
6. 为什么要继续演进到下一阶段。

## 2. 时间与 Git 口径

本仓库使用当前真实 Git 提交重建履历中的能力演进。标签表示“对应哪个履历阶段的可运行能力快照”，不是把今天的提交日期伪装成 2024 或 2025 年的历史提交。

| 履历时间 | 项目阶段 | Git 标签 | 主要变化 |
| --- | --- | --- | --- |

## 3. 2023.10–2024.12：Dify 企业知识助手与 RAG 工作流

### 业务背景

这个阶段的首要任务不是建设完整 Agent 平台，而是低成本验证企业知识问答是否有实际价值，例如制度查询、常见问题回答、内部资料检索和简单流程分流。

### 为什么使用 Dify

- 知识库、模型调用和工作流节点已有可视化能力，可以快速形成业务原型。
- 业务人员能够参与提示词、知识内容和流程规则调整。
- 在需求尚不稳定时，先验证问答效果比直接建设完整平台风险更低。

### 形成的能力

- 企业文档导入、切分和知识库检索。
- 基于检索上下文生成回答。
- 使用工作流节点连接知识查询和基础业务步骤。
- 根据试用反馈持续调整提示词、文档结构和召回策略。

### 暴露的问题

- 复杂权限过滤、业务状态和人工中断恢复难以完全由通用平台表达。
- 工具参数、错误返回和执行边界容易与平台实现耦合。
- 对幂等、审计、测试、故障注入和底层数据访问的控制不够细。
- 当业务逐渐稳定后，需要把关键能力沉淀为可测试、可复用的代码资产。

### 证据边界

这一阶段属于前序 Dify 项目，本仓库只说明它与自主平台的衔接关系，不把当前代码冒充为当年的 Dify 交付证据。

### 为什么进入下一阶段

需求验证完成后，重点从“能否快速做出来”转为“权限、状态和写操作能否被可靠控制”，因此开始建设 Python/LangGraph 自主底座。

## 4. 2024.09–2025 Q1：v0.1 自主 RAG 服务台底座

### 需要解决的问题

自主平台首先解决三个基础问题：回答必须带来源、权限必须在检索时生效、有副作用的建单必须经过人工确认并能够恢复。

### 技术选择

- 使用 Python 承载明确的数据模型、权限上下文和工具合同。
- 使用 Chroma 作为本地向量存储，降低 Demo 环境启动成本。
- 使用 LangGraph 表达可中断、可恢复的流程状态。
- 使用 SQLite checkpoint 保存人工审批前后的执行状态。
- 使用幂等键约束重复提交，避免审批恢复或请求重试生成重复工单。

### 核心流程

```text
用户请求
  → resolve_user 建立可信身份
  → 判断知识查询、状态查询或建单请求
  → 知识查询：按 visibility 在查询阶段过滤并返回引用
  → 状态查询：调用现有只读工具
  → 建单请求：权限校验 → LangGraph interrupt
  → 人工批准：Command(resume=...) → 幂等建单
```

### 相比 Dify 阶段的变化

- 权限从提示词要求变成代码中的查询条件和固定身份上下文。
- 写操作从普通工作流节点变成显式人工中断。
- 流程状态可以持久化并使用稳定 thread ID 恢复。
- 工具输入、返回值和异常开始具备可自动测试的合同。

### 仓库证据

- `src/auth/context.py`：只接受固定演示身份，未知身份 fail closed。
- `src/retrieval/chroma_store.py`：根据可信上下文生成允许的 `visibility` 集合，并在 Chroma 查询阶段传入过滤条件。
- `src/agent/workflow.py`：使用 `StateGraph`、`interrupt`、SQLite checkpointer 和 `Command(resume=...)` 实现建单审批恢复。
- `src/tools/platform_tools.py`：提供服务状态查询和带幂等约束的建单工具。
- `tests/test_v01_contracts.py`：检查只读用户查询、越权建单拒绝和未知身份拒绝。

### 当时没有做什么

- 工具只供项目内部代码调用，没有标准化 MCP 入口。
- 没有独立 Agent 间通信协议。
- 没有生产 IAM、真实工单系统或真实政企数据。
- Chroma 和 SQLite 适合本地运行，不代表生产部署选型已经完成。

### 为什么进入下一阶段

当工具数量增加、其他 Agent 或客户端也需要调用这些能力时，继续为每个调用方编写专用接口会造成重复适配，因此需要验证标准化工具暴露方式。

## 5. 2025 H1：v0.2 MCP 只读工具试点

### 需要解决的问题

`v0.1` 已经有可调用工具，但工具发现、参数 Schema 和调用方式仍与项目内部代码绑定。本阶段验证能否使用公开协议复用既有能力，同时不破坏权限和人工审批边界。

### 技术选择

- 复用官方 MCP Python SDK，不手写协议解析。
- 使用本地 stdio 作为最小接入方式，先验证注册、发现和调用合同。
- 只开放低风险的 `get_service_status`，不把 `create_ticket` 暴露给 MCP。
- MCP 入参只允许 `user_id` 和 `product_id`；可信角色仍由本地 `resolve_user` 建立。

### 核心流程

```text
本地 MCP 客户端
  → stdio
  → FastMCP 工具注册表
  → get_service_status(user_id, product_id)
  → resolve_user(user_id)
  → 复用 v0.1 的既有只读业务工具
```

### 相比 v0.1 的变化

- 工具拥有协议级名称、描述、输入 Schema 和只读注解。
- 外部 MCP 客户端可以发现并调用既有只读能力。
- 业务实现没有复制到 MCP 层，MCP 只是薄适配器。
- 写操作仍保留在 LangGraph 人工复核链，不因协议接入而绕过审批。

### 仓库证据

- `src/mcp_server.py`：通过 `FastMCP` 注册唯一工具 `get_service_status`，并复用 `resolve_user` 和原有业务工具。
- `scripts/mcp_smoke.py`：本地 stdio 的工具列表、Schema 和调用冒烟验证。
- `tests/test_mcp_contract.py`：验证只有预期的只读工具被注册。
- `v0.2.0-mcp-pilot`：保留该阶段使用的历史依赖 pin；当前主线使用维护版本。

### 当时没有做什么

- 没有开放远程 MCP 服务，也没有生产级认证、网关和限流。
- 没有证明第三方 MCP 客户端生态全部兼容。
- MCP 没有注册建单工具，不能绕过人工审批。
- MCP 解决的是“Agent 调工具”，不是“Agent 与 Agent 之间协作”。

### 为什么进入下一阶段

当诊断任务可能由独立 Agent 承担，并且存在较长执行时间、状态变化和失败回传时，简单工具调用不足以表达完整任务生命周期，因此需要验证 A2A 任务模型。

## 6. 2025 H2：v0.3 A2A 跨 Agent 通信验证

### 需要解决的问题

MCP 适合暴露工具，但独立 Agent 协作还需要描述对方能力、提交任务、查询状态、接收结果以及处理失败。本阶段选择一个边界清晰的“服务台 Agent 调用诊断 Agent”场景进行验证。

### 技术选择

- 使用官方 A2A SDK 表达 Agent Card、能力描述和任务对象。
- 将诊断 Agent 保持为只读能力，避免 PoC 同时引入业务写入风险。
- 明确 `submitted → working → completed/failed` 状态变化。
- 成功结果通过 artifact 返回；未知身份或工具失败必须进入 failed 状态。

### 核心流程

```text
服务台 Agent
  → 读取诊断 Agent Card
  → 提交服务诊断任务
  → submitted
  → working
  → completed + artifact
     或 failed + 明确错误
```

### 相比 v0.2 的变化

- 从一次工具调用扩展到有生命周期的跨 Agent 任务。
- 增加能力描述、任务 ID、状态和 artifact 等协作语义。
- 失败成为任务终态的一部分，而不是伪装成正常结果。
- MCP 继续负责工具层，A2A 用于 Agent 协作层，二者职责不混用。

### 仓库证据

- `src/a2a_poc.py`：构建诊断 Agent Card，并返回 submitted、working、completed 或 failed 状态。
- `scripts/a2a_demo.py`：运行本地诊断任务示例。
- `tests/test_a2a_poc.py`：检查 Agent Card、成功状态与 artifact、未知身份失败。
- `v0.3.0-a2a-poc`：保留该阶段的 A2A SDK 历史依赖快照。

### 当时没有做什么

- 这是本地协议模型 PoC，不是独立部署的远程 Agent 服务。
- 没有证明跨厂商、跨网络或生产级 A2A 互操作。
- 没有任务队列、分布式追踪、重试调度和多租户隔离。
- 只验证一个诊断 Agent，没有把所有业务都拆成服务。

### 为什么进入下一阶段

前三个阶段分别验证了 RAG 业务底座、标准工具调用和跨 Agent 任务模型。下一步不是继续增加孤立 PoC，而是把这些能力收敛到一个完整服务台业务流程中。

## 7. 2026：v1.0 多 Agent 工程化

### 需要解决的问题

早期版本能分别回答知识、调用工具和验证 Agent 通信，但企业业务需要统一入口、明确分流、人工门禁、审计记录和基础设施适配边界。本阶段把多个技术验证组合成一个可解释的服务台应用。

### 技术选择

- 使用 FastAPI 提供统一业务 API。
- 在同一进程内组织调度、知识、诊断、工单和审计五类逻辑 Agent。
- 保留 LangGraph 人工中断和恢复，避免多 Agent 编排绕过写操作门禁。
- 使用 OpenTelemetry span 和结构化审计事件记录路由、执行结果与耗时。
- 为 Milvus、PostgreSQL 和 Redis 提供窄适配器，使核心业务逻辑不直接依赖基础设施客户端。
- 默认仍使用 Chroma 和 SQLite，确保没有外部基础设施时也能运行 Demo。

### 核心流程

```text
FastAPI 请求
  → 可信身份解析
  → triage 调度
      ├─ knowledge：权限过滤 → RAG → 引用回答
      ├─ diagnostic：只读状态查询 → 诊断结果
      └─ ticket：权限校验 → 人工审批 → 幂等建单
  → audit 记录参与 Agent、动作、结果和耗时
  → API 返回统一结构
```

### 五类逻辑 Agent 的职责

| Agent | 职责 | 是否产生业务写入 |
| --- | --- | --- |
| triage | 判断请求进入知识、诊断还是工单路径 | 否 |
| knowledge | 执行带权限过滤的知识检索并返回引用 | 否 |
| diagnostic | 调用只读状态工具，判断是否已有可直接解决的信息 | 否 |
| ticket | 管理人工审批、中断恢复和幂等建单 | 是，必须经过门禁 |
| audit | 记录执行轨迹、参与 Agent、结果和耗时 | 只写审计信息 |

这里的“多 Agent”指职责拆分后的进程内协作，不等于五个独立部署的远程 Agent 服务。A2A 仍以 `v0.3` 的本地 PoC 形式保留，不能将其描述成已经完成分布式 Agent 平台。

### 相比 v0.3 的变化

- 从单一诊断 PoC 变成统一服务台业务编排。
- 增加 FastAPI 请求和审批恢复接口。
- 增加审计事件和 OpenTelemetry span。
- 明确本地默认实现与生产中间件适配器之间的边界。
- 不再把每种请求都当成建单：能够回答或诊断的问题直接返回结果。

### 仓库证据

- `src/agents/service_desk.py`：调度、知识、诊断、工单和审计协作。
- `src/api.py`：健康检查、任务提交和审批恢复接口。
- `src/agent/workflow.py`：写操作的人工中断与持久化恢复。
- `src/infrastructure/production_adapters.py`：Milvus 查询过滤、PostgreSQL 幂等记录和 Redis 任务状态适配边界。
- `tests/test_multi_agent.py`：检查诊断路径、工单人工门禁、审批权限和 Milvus 过滤条件。
- `tests/test_api.py`：检查 API 健康状态和审批需求返回。

### 当时没有做什么

- 没有接入真实政企 IAM、服务目录、监控平台或工单系统。
- 没有将五类 Agent 拆为独立服务。
- 生产中间件适配器的存在不等于集群、高可用和容灾已经验收。
- 没有 GUI、真实用户试用或第三方 MCP/A2A 兼容认证。

## 8. 2026：v1.1–v1.3 工程证据补强

`v1.1–v1.3` 不是三次新的技术时代，而是对 `v1.0` 多 Agent 工程的可验证性、基础设施边界和语义检索质量进行补强。

### v1.1.0-evidence：固定合同与故障注入

#### 目的

把“流程看起来能运行”转化为可重复检查的合同证据，覆盖正常分流以及常见失败路径。

#### 实现与证据

- 固定 100 条复合任务，覆盖知识、状态、允许建单和拒绝建单路径。
- 固定 30 条故障注入，覆盖未知身份、诊断超时、权限不足、中断恢复、重复执行和人工拒绝。
- `scripts/run_contract_suite.py` 从固定 Demo 定义生成合同数据，执行检查并生成 `docs/evidence/contract-report.json`。
- 当前留档结果为复合任务 100/100、故障注入 30/30。

#### 证据边界

这些是确定性合同检查，证明路由、Schema、引用映射、权限和门禁逻辑符合固定预期；不等于真实语义检索质量、真实业务联调或用户验收。

### v1.2.0-integration：本地容器联调与容量基线

#### 目的

验证生产适配边界是否真的能够连接对应中间件，而不是只有接口定义；同时给出一个可重复的本地容量参考。

#### 实现与证据

- 使用 Docker Compose 启动 PostgreSQL、Redis 和 Milvus 本地容器。
- PostgreSQL 验证相同幂等键返回原工单 ID。
- Redis 验证带 TTL 的任务状态写入和读取。
- Milvus 验证查询阶段的 `visibility` 过滤只返回允许文档。
- `docs/evidence/integration-report.json` 留档 3/3 个本地容器回环结果。
- `scripts/run_capacity_baseline.py` 对进程内 ASGI 入口执行 1,000 条混合请求、并发 20 的模拟负载。
- `docs/evidence/capacity-baseline.json` 记录 1,000/1,000 成功及本机延迟、吞吐结果。

#### 证据边界

- 容器回环只证明本机真实客户端和容器的一次有界联调。
- 容量数据来自进程内 ASGI 和确定性适配器，不是生产网络、真实 RAG 或真实中间件压测。
- 不能将 1,000 条模拟请求写成“日均 800+ 生产任务”。
- 没有证明生产高可用、备份、容灾、安全加固或持续负载能力。

### v1.3.0-semantic-eval：真实 Chroma 语义检索评测

#### 目的

`v1.1` 的知识用例验证的是固定合同，不能代替真实向量召回。本阶段使用实际嵌入模型和 Chroma 查询链，单独评估语义检索质量。

#### 实现与证据

- 使用固定 `BAAI/bge-small-zh-v1.5` revision，避免模型版本漂移。
- 使用虚构政企服务台文档生成可重复数据并写入 Chroma。
- 对 40 条知识问题执行真实向量查询，39 条在 Top 5 命中。
- 留档 `Hit@5=0.975`、`MRR=0.85`，并保留未命中的 `project-knowledge-031`。
- 同一次项目评测还记录工具选择 100/100、权限判断 100/100、工具 Schema 60/60。
- workflow 故障评测覆盖超时、权限拒绝、幂等重放、人工拒绝和进程重启恢复，结果 5/5。
- `docs/evidence/chroma-semantic-report.json` 和 `docs/evidence/workflow-fault-report.json` 保存机器可读摘要。

#### 为什么与 v1.1 的结果不矛盾

`v1.1` 的 `project-knowledge-031` 通过，表示它在确定性合同层满足预设路由、Schema、引用映射和权限要求；`v1.3` 中该问题未命中，表示真实向量检索的 Top 5 没有召回目标文档。两套评测的对象不同，因此必须分别报告，不能把合同通过率包装成语义召回率。

#### 快照隔离

评测不会直接修改正常运行库，而是复制 Chroma 数据到本次运行目录，在副本上执行查询和故障场景，并比较正常库前后的文件哈希。这证明本轮评测未改变正常库，不代表具备生产备份或容灾能力。

#### 证据边界

数据集是固定虚构 Demo 数据，不包含真实企业文档或真实用户信息。结果可以证明当前模型和数据集上的可重复检索表现，不能外推为真实企业语料效果，也不能替代 Milvus 语义迁移评测。

## 9. 技术为什么按这个顺序出现

| 阶段 | 当时最重要的问题 | 当时没有提前做后续能力的原因 |
| --- | --- | --- |
| Dify | 快速验证知识问答是否值得做 | 需求未稳定，先搭大型自主平台成本过高 |
| v0.1 | 权限、状态、审批和幂等可控 | 工具数量和跨系统调用需求尚未成为主要矛盾 |
| v0.2 | 工具如何被标准发现和调用 | MCP 不负责长任务和 Agent 生命周期 |
| v0.3 | Agent 如何交换任务、状态和结果 | 先用单一诊断场景验证协议，不急于分布式部署 |
| v1.0 | 如何形成统一业务闭环 | 经验证的能力已足够进入整合阶段 |
| v1.1–v1.3 | 如何让能力可重复验证 | 工程结论需要合同、联调和语义指标支持 |

这条路线的核心不是追逐技术名词，而是每一次升级都由上一阶段暴露的问题驱动。

## 12. 面试讲解主线

可以将整个演进压缩成以下表述：

> 项目最初通过 Dify 快速验证企业知识助手和 RAG 工作流。随着权限、状态和人工审批要求增加，我从 2024 年下半年开始将核心能力下沉到 Python 和 LangGraph，建立查询期权限过滤、人工中断恢复和幂等建单。2025 年上半年使用 MCP 标准化只读工具接入，下半年通过 A2A 验证诊断 Agent 的任务状态和结果回传。2026 年将这些能力收敛为调度、知识、诊断、工单和审计五类逻辑 Agent，并通过 FastAPI、中间件适配、OpenTelemetry、固定评测集、故障注入和真实语义检索补齐工程证据。

这段表述必须与证据边界一起使用：仓库证明的是可运行的本地工程 Demo、自动化合同、本地容器联调和固定虚构数据评测，不证明真实国企生产部署、真实日均任务量或用户验收。

## 13. 为什么不拆成多个仓库

这些标签表达的是同一产品的增量演进，而不是互不相关的四套样例。保留在一个仓库可以让调用链、代码差异、迁移成本和技术取舍连续可见，也避免重复复制权限、工具和测试代码。需要查看某个时期时，直接读取或检出对应标签即可。

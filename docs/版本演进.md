# 版本演进说明

## 时间线口径

本仓库用今天的真实 Git 提交重建项目能力演进。标签说明的是“履历对应阶段”，不是把今天的提交伪装成 2024 或 2025 的历史提交。

这条路线与前序 Dify 项目可自然衔接：

- 2023.10-2024.12：使用 Dify 快速搭建企业知识助手和 RAG 工作流。
- 2024.09 起：把关键能力下沉到自主可控的 Python/LangGraph 服务台底座。
- 2025 H1：在协议和 SDK 已可用后验证 MCP 只读工具接入。
- 2025 H2：在 A2A 发布后验证跨 Agent 任务描述、状态和结果回传。
- 2026：把验证过的能力收敛为带权限、人工门禁、追踪和业务接口的多 Agent 工程。

两个项目在 2024.09-2024.12 有意重叠：Dify 项目仍在维护和交付，新平台同时做能力下沉与替代验证。这比“某天突然完全重写”更符合企业软件渐进迁移。

## v0.1：RAG 服务台底座

核心问题是让回答有来源、权限在查询阶段生效，以及让有副作用的建单可中断恢复。

主要证据：

- src/retrieval/chroma_store.py 在查询阶段加入 visibility 过滤。
- src/auth/context.py 只接受固定演示身份，未知身份 fail closed。
- src/agent/workflow.py 在建单前执行 LangGraph interrupt。
- src/tools/platform_tools.py 使用幂等键避免重复建单。

## v0.2：MCP 只读试点

MCP 不是“把全部业务注册出去”。本阶段只注册服务状态查询，用于验证外部 MCP 客户端如何发现和调用已有只读能力；写操作仍保留在内部人工复核链。

历史 pin 使用 mcp==1.9.4，该版本于 2025-06-12 发布，因此与“2025 上半年完成 MCP 试点”一致。

## v0.3：A2A PoC

本阶段只有一个独立诊断 Agent，验证：

- Agent Card 描述能力。
- submitted、working、completed/failed 状态流转。
- artifact 结果回传。
- 身份未知或工具失败时返回 failed，而不是伪装成功。

历史 pin 使用 a2a-sdk==0.3.6，该版本于 2025-09-09 发布。PoC 不等于生产级多 Agent。

## v1.0：多 Agent 工程化

调度、知识、诊断、工单、审计 Agent 在同一服务台业务中协作。FastAPI 提供业务系统入口，OpenTelemetry 提供 span；Milvus、PostgreSQL、Redis 通过独立适配器与核心编排解耦。

本地默认仍使用 Chroma 和 SQLite，以便任何人不连接外部基础设施也能运行 Demo。生产适配器存在不等于真实集群已经验收。

## 为什么不拆成四个仓库

四个标签表达的是同一个产品的增量演进。一个仓库能让代码差异、迁移成本和技术取舍可见，也能避免四套样例之间重复复制。需要查看某阶段时直接检出对应标签即可。

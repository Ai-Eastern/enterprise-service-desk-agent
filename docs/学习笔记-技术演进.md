# 学习笔记：从 RAG 单 Agent 到多 Agent 服务台

## 1. 先分清工具协议和业务编排

MCP 解决“能力如何被发现和调用”，不替业务系统决定谁能调用、是否需要审批。A2A 解决 Agent 之间如何描述能力和交换任务，也不自动提供企业权限、幂等和审计。

因此本项目把职责拆开：

- 权限上下文由业务服务端建立，不能信任调用方传入 role。
- MCP 只开放只读工具。
- A2A 负责任务卡片、状态和结果。
- LangGraph 负责写操作前的人机协作和恢复。

## 2. 什么问题不需要建单

- 知识库已有明确操作步骤。
- 查询结果表明服务已知异常且正在处理中。
- 用户只是查看状态或制度。
- 问题信息不足，需要先追问。
- 用户身份未知或无建单权限。

只有自助路径无法解决、信息完整且权限通过时，系统才生成工单草案；真正写入仍需人工确认。

## 3. 为什么先做单 Agent，再做多 Agent

单 Agent 阶段先证明权限、检索、工具与人工门禁正确。过早拆 Agent 会把同一个函数调用包装成复杂消息传递，却没有新的业务价值。

当诊断能力需要独立部署、任务有较长生命周期、不同团队拥有不同能力或需要独立扩缩容时，再引入 A2A 和多 Agent 才有明确收益。

## 4. 本地 Demo 与生产工程的差别

本地 Chroma/SQLite 让示例可复现；生产环境通常需要 Milvus/PostgreSQL/Redis、统一身份、密钥管理、审计存储、限流和容灾。代码中的 production adapters 只证明接口设计，不代表真实集群联调已经完成。
